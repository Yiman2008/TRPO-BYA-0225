# Практическая работа №5 — PHP ООП. Классы, конструкторы и модели предметной области

PHP-приложение, которое строит **каталог товаров** из `products.json` и `categories.json` через объекты `Product` и `Category` и сервис `CatalogService`. Есть фильтр по категории и наличию, агрегаты (средняя цена, сумма, количество), сверка классов с `class_requirements.csv` и демонстрация некорректных конструкторов.

**Технологии:** PHP 8.1+ (constructor property promotion, `match`, nullsafe-оператор `?->`), HTML, CSS.

## Запуск

```bash
cd pr05
php -S localhost:8000 -t public
```

Открыть <http://localhost:8000>. Требуется только PHP 8.1+.

## Модели по `class_requirements.csv`

| Класс | Свойство | Тип | Откуда в данных |
|---|---|---|---|
| Product | `id` | int | `products.json → id` |
| Product | `name` | string | `name` |
| Product | `price` | float | `price` |
| Product | `categoryId` | int | `category_id` — связь с `Category` по идентификатору |
| Category | `id` | int | `categories.json → id` |
| Category | `name` | string | `name` |

Дополнительно у `Product` есть `active` (bool): поле есть в `products.json` и влияет на поведение («в продаже / нет в продаже», фильтр), но не обязательно по требованиям — поэтому это последний параметр конструктора со значением по умолчанию `true`. Других свойств без смысла не добавлено. На странице в блоке «Соответствие class_requirements.csv» Reflection проверяет, что каждое свойство существует и имеет нужный тип (6 из 6 ✔).

## Что изменилось после шага 4 (методы предметной области)

Вместо набора getter/setter у `Product` появились методы, которые описывают поведение товара:

| Метод | Что делает |
|---|---|
| `isAvailable(): bool` | можно ли купить товар (`active`) |
| `belongsTo(Category $c): bool` | относится ли товар к категории |
| `priceWithDiscount(float $percent): float` | цена со скидкой; при скидке вне 0–100 — `InvalidArgumentException` |
| `priceSegment(): string` | ценовой сегмент `budget` (< 800), `standard`, `premium` (≥ 1500) |
| `isPriceInRange(?float $min, ?float $max): bool` | попадание в ценовой диапазон |
| `deactivate(): Product` | новый объект «снят с продажи», исходный не меняется |

Геттеры оставлены только для значений, которые нужны для вывода (`id()`, `name()`, `price()`, `categoryId()`), сеттеров нет: состояние задаётся конструктором. Шаблон теперь не считает скидку и сегмент сам, а спрашивает об этом объект.

## Конструктор и `InvalidArgumentException`

Конструктор не даёт создать объект в неверном состоянии:

- `Product`: `id ≤ 0`, пустое (после `trim`) название, отрицательная цена, `categoryId ≤ 0`;
- `Category`: `id ≤ 0`, пустое название.

`CatalogService` ловит исключение для каждой записи JSON: битая запись пропускается, а сообщение выводится вверху страницы, остальной каталог продолжает работать. В блоке «Проверка некорректного конструктора» показаны 4 неудачных вызова и 1 удачный (`new Product(15, "Клавиатура", 3500, 2)`).

## Схема Product → CatalogService → index.php

```
data/products.json ─┐
data/categories.json┴─► CatalogService ──► list<Product>, Category ──► public/index.php ──► HTML
                         │ читает JSON (JSON_THROW_ON_ERROR)              │ читает $_GET (фильтр)
                         │ создаёт объекты через new Product(...)         │ вызывает filterByCategory(),
                         │ filterByCategory(), onlyAvailable(),           │   onlyAvailable(), averagePrice()
                         │ averagePrice(), totalPrice(), countByCategory()│ форматирует цену money()
                         ▼                                                │ экранирует e() и выводит карточки
                     Product / Category
                     данные + поведение: isAvailable(), priceWithDiscount(), priceSegment() …
```

- **Product / Category** — состояние одной сущности и операции над ней. Ничего не знают о файлах, запросах и HTML.
- **CatalogService** — знает, где лежат данные и как из них сделать объекты; операции над набором товаров (фильтр, агрегаты, поиск категории).
- **index.php** — обрабатывает GET-фильтр (валидирует `category` через `FILTER_VALIDATE_INT`), просит у сервиса нужную выборку и выводит её. Форматирование цены (`money()`) и экранирование (`e()`) — тоже здесь, потому что это задачи представления.

Если внутри `Product` цену начнут хранить, например, в копейках (int), HTML менять не придётся, пока метод `price()` возвращает рубли.

## Фильтр каталога

GET-форма: `?category=2&available=1`. Обработка фильтра находится в `index.php`, а не в `Product`.

| Запрос | Результат |
|---|---|
| без параметров | 12 из 12, 2 карточки «Нет в продаже» (товары 5 и 10) |
| `?category=2` | 4 товара «Оборудование» |
| `?category=2&available=1` | 3 товара |
| `?category=99`, `?category=abc`, `?category[]=1` | предупреждение «Такой категории нет», показаны все товары, без warning |

Проверка всех строк `products.json` (шаг 13): все 12 товаров создаются, цены выводятся с копейками (`436,50 ₽`), категории подставляются по `category_id`; если категории нет в `categories.json`, выводится «Без категории», а если по фильтру нет товаров — сообщение «По выбранным условиям товаров нет».

## Почему ручные `require_once` неудобны при росте проекта

Сейчас `index.php` подключает 4 файла вручную, а `CatalogService` — ещё 2. С ростом проекта: нужно помнить порядок подключения и путь к каждому классу; при переименовании или переносе файла придётся править все `require`; легко подключить лишнее или забыть нужное и получить `Class not found`. Решение — **автозагрузка**: `spl_autoload_register()` или Composer с PSR-4 (`"App\\": "src/"`) и пространствами имён — класс подгружается автоматически при первом обращении.

## Как на защите добавить свойство в конструктор

Пример: добавить `private ?string $sku = null` последним параметром `Product::__construct`, передать `$row['sku'] ?? null` в `CatalogService`, добавить метод `hasSku()` и вывести артикул в карточке — остальные части не меняются.
